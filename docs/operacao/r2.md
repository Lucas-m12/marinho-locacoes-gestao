# Cloudflare R2

Os arquivos (fotos de unidade, dano e checklist, vídeo do teste, documentos de clientes e comprovantes) ficam num bucket **privado** do R2 (ADR 0012). O servidor nunca recebe os bytes: ele assina uma URL de `PUT` para o navegador enviar direto ao bucket e, depois, uma URL de leitura de 10 minutos. Os backups do Postgres ficam em outro bucket, com outro token.

## Buckets

| Bucket | Para quê | Token | CORS | Ciclo de vida |
| --- | --- | --- | --- | --- |
| `marinho-dev` | arquivos do desenvolvimento | token de dev | `http://localhost:3001` | — |
| `marinho-prod` | arquivos da produção | token de produção | `https://sistema.marinholocacoes.com` | — |
| `marinho-backups` | backups diários do Postgres | token de backup | nenhum (o navegador nunca acessa) | apagar depois de 30 dias |

Buckets separados garantem que testes nunca toquem nos arquivos reais e que quem tem o token dos uploads não consiga apagar os backups.

## Variáveis do servidor

Ficam em `apps/server/.env` (desenvolvimento) e em `/opt/marinho/.env` na VPS (produção). Nunca vão para o repositório.

| Variável | De onde vem | Sensível? |
| --- | --- | --- |
| `R2_ACCOUNT_ID` | Painel → **R2 Object Storage** → "Account ID" (na lateral) | não |
| `R2_ACCESS_KEY_ID` | Access Key ID do token do bucket | não |
| `R2_SECRET_ACCESS_KEY` | Secret Access Key do token, mostrado uma única vez | **sim** |
| `R2_BUCKET` | `marinho-dev` ou `marinho-prod` | não |
| `R2_BACKUP_BUCKET` | `marinho-backups` (só produção; só a tarefa de backup usa) | não |
| `R2_BACKUP_ACCESS_KEY_ID` | Access Key ID do token de backup | não |
| `R2_BACKUP_SECRET_ACCESS_KEY` | Secret Access Key do token de backup | **sim** |
| `R2_ENDPOINT` | vazio. Só serve para testes locais com um S3 falso | não |

"Sensível" é como o varlock trata a variável: valores sensíveis são escondidos dos logs e **bloqueiam** qualquer resposta da API que os contenha. O Account ID, o bucket e o Access Key ID vão dentro de toda URL assinada, então não podem ser sensíveis (o `apps/server/src/env-schema.test.ts` confere isso). O segredo de verdade é a Secret Access Key, que nunca sai do servidor.

## Produção: passo a passo no painel

### 1. Criar os buckets

**R2 Object Storage → Create bucket**. Crie `marinho-prod` e depois `marinho-backups`, com localização automática e classe **Standard**. Nenhum dos dois fica público: não ligue "Public access" nem domínio próprio.

### 2. Criar os tokens

**R2 Object Storage → Manage API tokens → Create API token**, uma vez para cada bucket:

| Campo | Token de produção | Token de backup |
| --- | --- | --- |
| Nome | `marinho-prod-servidor` | `marinho-backups-servidor` |
| Permissão | **Object Read & Write** | **Object Read & Write** |
| Buckets | só `marinho-prod` | só `marinho-backups` |
| Validade (TTL) | sem expiração | sem expiração |

Ao criar, a Cloudflare mostra o **Access Key ID** e a **Secret Access Key** (esta só uma vez). Copie direto para o `/opt/marinho/.env` e para o gerenciador de senhas.

### 3. CORS do `marinho-prod`

**marinho-prod → Settings → CORS Policy → Add CORS policy**, cole e salve:

```json
[
  {
    "AllowedOrigins": ["https://sistema.marinholocacoes.com"],
    "AllowedMethods": ["PUT", "GET"],
    "AllowedHeaders": ["Content-Type"],
    "MaxAgeSeconds": 3600
  }
]
```

- `PUT` é o envio. A URL assinada inclui o `Content-Type` na assinatura, então o navegador precisa mandar exatamente o tipo pedido em `uploads.requestUpload` (o front já usa os `headers` devolvidos).
- `GET` é a leitura pelas URLs de 10 minutos de `files.getDownloadUrl`.
- A origem é exata: com `https`, sem barra no fim, sem `www`.

No `marinho-dev`, a mesma regra com `"http://localhost:3001"` no lugar.

### 4. Ciclo de vida do `marinho-backups`

**marinho-backups → Settings → Object lifecycle rules → Add rule**:

| Campo | Valor |
| --- | --- |
| Nome | `apagar-backups-30-dias` |
| Aplicar a | prefixo `postgres/` |
| Ação | **Delete uploaded objects** depois de **30 dias** |

Mantenha também a regra padrão que já vem no bucket (cancelar envios em partes incompletos depois de 7 dias): ela limpa sobras de um backup que caiu no meio do envio.

A retenção é feita pelo bucket, não pelo código: a tarefa só envia. Para guardar mais tempo, mude os dias aqui.

**Proteção extra (opcional):** em **Settings → Bucket lock rules**, uma regra de 7 dias para o prefixo `postgres/` impede que qualquer pessoa ou token apague um backup recente, mesmo com o token vazado. A regra de ciclo de vida (30 dias) continua funcionando depois desse prazo.

## Como o fluxo de upload confere o arquivo

1. `uploads.requestUpload` valida finalidade, tipo e tamanho (imagem até 10 MB, vídeo até 50 MB, documento até 10 MB), grava o `Upload` como `PENDING` e devolve a URL de `PUT` válida por 10 minutos. A chave é `<finalidade>/<aaaa>/<mm>/<uuid>.<ext>`.
2. O navegador envia o arquivo direto ao R2.
3. `uploads.completeUpload` faz `HEAD` no objeto. Se o tamanho ou o tipo não baterem com o pedido, apaga o objeto e devolve `PRECONDITION_FAILED` (`UPLOAD_INVALID`). Se baterem, marca o `Upload` como `COMPLETED`.
4. Fotos, documentos, mídia do checklist e comprovantes só aceitam upload `COMPLETED`, do próprio usuário e com a finalidade certa.

Duas tarefas agendadas limpam o bucket ([rotina.md](rotina.md)):

- `cleanup-uploads`, de hora em hora: apaga do R2 e do banco os uploads `PENDING` com mais de 24 h (o navegador pediu a URL e nunca concluiu).
- `purge-customer-documents`, às 03:30: apaga os documentos de clientes sem locação há mais de 24 meses (ADR 0016) e registra no histórico só o id e o tipo de cada documento.

## Conferir se está funcionando

Com o servidor e o front em modo `http`, envie uma foto de unidade e abra a foto depois. Se o navegador mostrar erro de CORS no console, confira a regra acima e a origem exata. Se a API devolver erro 500 ao pedir o upload, veja `docker compose logs server`: uma mensagem `DETECTED LEAKED SENSITIVE CONFIG` indica uma variável de R2 marcada como sensível no `apps/server/.env.schema`.
